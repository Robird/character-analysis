# 综合改进方案：场景展开 + 三轮递进提取

两个思路的优势互补很清晰：

- **思路二的优势**：场景中间层的设计（特别是 recurring/singular 的区分）、动作类型分类框架（action_taxonomy）作为结构化引导
- **我之前思路的优势**：三轮递进提取（叙事→维度补充→未选择路径）、对长周期子时期的处理、第三轮的"决策上下文"对训练数据格式的直接贡献

合并后的核心架构：

```
sub_period
  └─ Phase 2A: 场景展开（含 recurring/singular 标注）
       └─ Phase 2B: 动作提取（三轮递进，以 taxonomy 为引导框架）
            └─ Phase 2C: 决策上下文补充（未选择路径，仅对决策类动作）
```

---

## Phase 2A：场景展开

每个场景是 `Scene` 模型的一个实例，LLM 通过 `output_scene` 工具逐条产出，
由 Agent 层自动校验字段类型与完整性。

### 产出结构

```python
from pydantic import BaseModel, Field
from typing import Literal, TypeAlias

SceneType: TypeAlias = Literal["singular", "recurring"]
ActionType: TypeAlias = Literal[
    "verbal",
    "physical",
    "social",
    "instrumental",
    "expressive",
    "perception",
    "interpretation",
    "emotion",
    "recall",
    "judgment",
    "decision",
    "desire",
    "suppression",
    "belief_update",
]
DecisionConfidence: TypeAlias = Literal["坚定", "犹豫", "被迫", "冲动"]

class Scene(BaseModel):
    """Phase 2A 产出：一个时空连续的具体事件或情境。"""
    name: str = Field(description="场景名")
    scene_type: SceneType = Field(
        description="singular: 一次性事件；recurring: 反复发生的行为模式"
    )
    time_in_period: str = Field(description="此场景在子时期中的相对时间位置")
    participants: list[str] = Field(description="在场人物")
    setting: str = Field(description="地点/环境")
    mood: str = Field(description="主基调")
    sketch: str = Field(description="50-80字的场景概述，描述发生了什么")
    frequency: str = Field(
        default="",
        description="[仅 recurring] 大约发生的频率和持续时间跨度",
    )


class SubPeriodRef(BaseModel):
    """Phase 1 子时期的结构化引用，字段与 Phase 1 的 ``SubPeriod`` 模型一致。

    供 Phase 2 管线以类型安全的方式访问 ``phase1-timeline.json`` 中的子时期信息，
    避免整合代码中裸 dict 访问带来的字段名猜测。
    """
    name: str
    time_range: str
    core_situation: str
    opening_event: str
    closing_event: str = ""


class LifeStageRef(BaseModel):
    """Phase 1 主要阶段的结构化引用。"""
    name: str
    time_range: str
    summary: str
    sub_periods: list[SubPeriodRef]


class Phase1TimelineData(BaseModel):
    """Phase 1 时间轴主体。"""

    life_stages: list[LifeStageRef]


class Phase1Timeline(BaseModel):
    """Phase 1 产出 ``phase1-timeline.json`` 的反序列化模型。

    与仓库当前真实落盘结构对齐：人物元信息位于顶层，时间轴主体位于 ``data`` 字段。
    """

    character: str
    data: Phase1TimelineData
```

### 场景展开 Agent

```python
from agent import Agent

_SCENE_DECOMP_SYSTEM_PROMPT = (
    "你是一位叙事分析专家，擅长将一段人生时期拆解为具体、有序的场景序列。"
    "每个场景是一个时空连续的、可'拍成一个镜头'的具体事件或情境。"
    "你只通过 output_scene 工具调用输出场景——每个场景单独一次调用，"
    "按时间/因果顺序依次发出。"
)

def decompose_scenes(
    character_profile: str,
    sub_period,
    client: LLMClient,
) -> list[Scene]:
    """将子时期展开为有序的场景序列。"""
    agent = Agent(_SCENE_DECOMP_SYSTEM_PROMPT, client=client)
    agent.add_output_tool(
        "output_scene",
        Scene,
        "用此工具输出一个场景。每个场景单独一次调用，按时间顺序依次发出。",
    )
    prompt = (
        f"人物：{character_profile}\n"
        f"时期：{sub_period.name}\n"
        f"时间范围：{sub_period.time_range}\n"
        f"处境：{sub_period.core_situation}\n"
        f"起始事件：{sub_period.opening_event}\n"
        f"结束事件：{sub_period.closing_event}\n\n"
        "请将此时期展开为一个有序的场景序列。\n"
        "要求：\n"
        "1. 覆盖完整时间线，不跳过'平淡'的部分。\n"
        "2. 标志性事件、日常典型情境、过渡场景都要包括。\n"
        "3. 对长时间跨度中反复发生的行为模式，用 recurring 场景来代表"
        "——在 frequency 字段说明大约频率，sketch 描述一次典型实例。\n"
        "4. 场景之间保持时间/因果顺序。\n"
        "5. 注意：opening_event 和 closing_event 是子时期的转折锚点——它们中蕴含的关键动作"
        "和事件必须被覆盖，宁可边界处偶发重叠，也不能遗漏。"
        "opening_event 可作为本时期第一个场景的核心内容自然展开"
        "（即便上一子时期的末尾可能也触及了同一事件，从不同视角或粒度覆盖完全可以接受）。"
        "closing_event 标志本时期的结束，可在最后一个场景中体现。\n\n"
        f"目标数量（根据时期跨度自适应）：\n"
        f"  - 数周跨度：5-8 个场景\n"
        f"  - 数月跨度：8-12 个场景\n"
        f"  - 数年跨度：12-18 个场景\n"
        f"注意：若时期信息稀疏（仅有静态处境描述而无具体事件链），"
        f"以 recurring 场景为主，不强凑 singular 数量。"
    )
    result = agent.run(prompt, temperature=0.4)
    return result.by_tool("output_scene")
```

### 单场景子时期的直接转换

对于跳过展开的子时期，用一次轻量 Agent 调用将其整理为一个 `Scene`，
而非手工拼接字段——保证 participants / setting / mood 的提取质量一致。

```python
_SCENE_FROM_SP_SYSTEM_PROMPT = (
    "你是一个文本分析辅助程序。将一个人生子时期的信息整理为一个 Scene 结构。"
    "你只通过 output_scene 工具调用输出结果。"
)

def scene_from_sub_period(sub_period, client: LLMClient) -> Scene:
    """将单场景子时期转换为一个 Scene。"""
    agent = Agent(_SCENE_FROM_SP_SYSTEM_PROMPT, client=client, max_iterations=4)
    agent.add_output_tool(
        "output_scene",
        Scene,
        "用此工具输出从子时期提取的单个场景。",
    )
    prompt = (
        f"子时期名称：{sub_period.name}\n"
        f"时间范围：{sub_period.time_range}\n"
        f"核心处境：{sub_period.core_situation}\n"
        f"起始事件：{sub_period.opening_event}\n"
        f"结束事件：{sub_period.closing_event}\n\n"
        "请将以上信息整理为一个 scene_type='singular' 的场景。"
        "从核心处境和起止事件中推断 participants / setting / mood，"
        "以 core_situation 为主要依据撰写 sketch。"
    )
    result = agent.run(prompt, temperature=0.0, query_status=False)
    scenes = result.by_tool("output_scene")
    if scenes:
        return scenes[0]
    # 兜底：用最直接的字段映射构造一个最小 Scene
    # 注意：participants/setting/mood 为空时，下游 Phase 2B R1 的 prompt 中
    # "在场人物：" 等标签会出现空值。LLM 通常会根据 sketch 自行推断，
    # 但若频繁触发此兜底，应排查上游 Agent 为何未产出合法 Scene。
    return Scene(
        name=sub_period.name,
        scene_type="singular",
        time_in_period=sub_period.time_range,
        participants=[],
        setting="",
        mood="",
        sketch=sub_period.core_situation,
    )
```

**改进点**：所有 LLM 产出统一为 Agent 结构化工具调用（`output_scene`），消除裸 JSON
文本解析；新增 `scene_from_sub_period` 保证单场景子时期的 participants/setting/mood
提取质量与展开路径一致；用 LLM Agent 做单场景判定替代硬编码关键词匹配（见下方「跳过逻辑」）。

### 跳过逻辑

不依赖硬编码关键词，改用 LLM Agent 做结构化判断——与 Phase 0 的
`extract_meta`、Phase 1 的时间线划分保持一致的 Agent 调用范式。

先定义产出结构：

```python
from pydantic import BaseModel, Field

class SceneDecompositionVerdict(BaseModel):
    """对单个子时期是否需要场景展开的结构化判断。"""
    needs_decomposition: bool = Field(description="是否需要场景展开")
    reason: str = Field(description="判断依据，如'单日内的单一事件'或'跨度数年的漫长时期'")
```

Agent 构造与判断函数：

```python
from agent import Agent

_SCENE_JUDGMENT_SYSTEM_PROMPT = (
    "你是一个文本分析辅助程序。你的任务是根据子时期的时间范围描述，"
    "判断该子时期是否需要进行场景展开（decomposition）。"
    "规则：如果时间范围描述表明这是一个单日/单场景的短事件"
    "（如'一个傍晚''当天下午''那个凌晨''某次交谈'），则不需要展开；"
    "如果时间跨度达到数周或更长，则需要展开。"
    "你只通过工具调用输出判断结果，不输出其他内容。"
)

def needs_scene_decomposition(sub_period, client: LLMClient) -> bool:
    """用 LLM Agent 判断子时期是否需要场景展开。"""
    agent = Agent(_SCENE_JUDGMENT_SYSTEM_PROMPT, client=client, max_iterations=4)
    agent.add_output_tool(
        "output_verdict",
        SceneDecompositionVerdict,
        "用此工具输出对当前子时期是否需要场景展开的判断。",
    )
    prompt = (
        f"子时期名称：{sub_period.name}\n"
        f"时间范围描述：{sub_period.time_range}\n"
        f"核心处境：{sub_period.core_situation}\n\n"
        "请判断此子时期是否需要场景展开。"
    )
    result = agent.run(prompt, temperature=0.0, query_status=False)
    verdicts = result.by_tool("output_verdict")
    if not verdicts:
        # 兜底：未能取得结构化判断时，保守地展开
        return True
    return verdicts[-1].needs_decomposition
```

为什么改用 LLM Agent：

- 关键词匹配无法可靠地区分「三年流浪」「数月漂泊」（需要展开）与「某个秋日午后」
  （不需要展开）——两者的自然语言时间粒度差异只能由语义理解捕获。
- 产出带有 `reason` 字段，方便审计与调试——知道 LLM *为什么* 做了某个判断。
- 与管线其他 Agent 调用（Phase 0 的元信息提取、Phase 2A/2B/2C 的主体分析）
  共用同一 `LLMClient`，不引入新依赖。
- 此判断任务极轻量（单次调用、`temperature=0.0`、`max_iterations=4`），
  对于 5000 人物 × 平均 8 个子时期 = ~40K 次额外调用，在总体预算中占比微小。

对于简·爱的24个子时期，大约：
- 8-10个是单场景（红房子事件、果园求婚、婚礼中断、重逢等）→ 跳过，直接进 2B
- 14-16个需要展开 → 每个产出 5-18 个场景

预计总场景数：~8 个直通 + ~160 个展开 = **约 170 个场景单元**

## Phase 2B：动作提取（核心改进——融合两种思路）

这里是最关键的融合。思路二的 action_taxonomy 作为**引导框架**，我之前的三轮递进改造为**两轮**（因为 taxonomy 本身已经覆盖了"维度补充"的大部分功能，不需要独立的第二轮了）。

### 第一轮：以 taxonomy 引导的全量提取

每个动作是 `Action` 模型的一个实例，LLM 通过 `output_action` 工具逐条产出，
按时间/因果顺序依次调用。

#### 产出结构

```python
class Action(BaseModel):
    """Phase 2B Round 1 产出：场景内的一个动作单元。"""
    seq: int = Field(ge=1, description="在场景内的顺序号，从1开始")
    type: ActionType = Field(
        description=(
            "动作类型，必须为 taxonomy 中定义的14类之一："
            "verbal / physical / social / instrumental / expressive / "
            "perception / interpretation / emotion / recall / judgment / "
            "decision / desire / suppression / belief_update"
        )
    )
    description: str = Field(description="动作的具体描述，一句话")
    detail: str = Field(default="", description="可选的补充细节或上下文")


DECISION_RELATED_ACTION_TYPES: tuple[ActionType, ...] = (
    "decision",
    "suppression",
    "social",
)
```

#### 动作提取 Agent

```python
# 动作类型 taxonomy（嵌入 system prompt，引导 LLM 覆盖各维度）
_ACTION_TAXONOMY = (
    "外部动作："
    "verbal（说了什么、对谁、什么语气、什么意图）、"
    "physical（身体动作、位移、姿态）、"
    "social（服从/反抗/讨好/回避/合作/对抗）、"
    "instrumental（使用物品、读写、劳作）、"
    "expressive（哭、笑、沉默、颤抖、叹息）；"
    "内部动作："
    "perception（注意到/观察到了什么）、"
    "interpretation（如何理解当前情境）、"
    "emotion（产生什么情绪、情绪如何变化）、"
    "recall（想起了什么）、"
    "judgment（对人或事做出什么评价）、"
    "decision（做了什么决定，包括'决定忍耐''决定不说'）、"
    "desire（想要什么、渴望什么）、"
    "suppression（压抑了什么冲动）、"
    "belief_update（信念/认知是否发生变化）"
)

_ACTION_EXTRACT_SYSTEM_PROMPT = (
    "你是一位动作分析专家。给定一个场景，你逐条列举目标人物在其中的全部动作，"
    "包括外部可观察行为和内部心理过程。"
    "你只通过 output_action 工具调用输出动作——每个动作单独一次调用，"
    "按时间/因果顺序依次发出。"
    f"动作类型必须从以下 taxonomy 中选择：{_ACTION_TAXONOMY}"
    "每种类型都考虑是否存在，但不强求每种都有。"
)

def extract_actions_with_taxonomy(
    character_profile: str,
    scene: Scene,
    sub_period,
    client: LLMClient,
) -> list[Action]:
    """对单个场景做 taxonomy 引导的全量动作提取。"""
    agent = Agent(_ACTION_EXTRACT_SYSTEM_PROMPT, client=client)
    agent.add_output_tool(
        "output_action",
        Action,
        "用此工具输出场景中的一个动作。每个动作单独一次调用，按时间/因果顺序。",
    )
    prompt = (
        f"人物：{character_profile}\n"
        f"场景：{scene.name}\n"
        f"场景类型：{scene.scene_type}\n"
        f"在场人物：{', '.join(scene.participants)}\n"
        f"环境：{scene.setting}\n"
        f"基调：{scene.mood}\n"
        f"概述：{scene.sketch}\n"
        f"所属子时期背景：{sub_period.core_situation}\n\n"
        f"请列举 {character_profile} 在此场景中的全部动作，包括外部动作和内部动作。\n"
        "按时间/因果顺序排列，每个动作标注 type。\n\n"
        "注意：\n"
        "- 如果场景类型是 recurring，描述的是一次典型实例中的动作序列。\n"
        "- 粒度要求：一个动作 ≈ 一个可观察的行为单元或一次内心转变。\n"
        "- 不要合并多个动作为一条笼统描述。\n"
        "- 预期产出 15-30 个动作。"
    )
    result = agent.run(prompt, temperature=0.4)
    return result.by_tool("output_action")
```

**相比纯三轮方案的改进**：taxonomy 嵌入 system prompt 作为引导框架（而非靠第二轮
追问补充），LLM 在第一轮就被迫覆盖各个维度。

**相比纯 taxonomy 方案的改进**："按时间/因果顺序依次发出"保留了叙事序列结构，产出
天然有序，而非按类型分桶堆砌——这对后续转换为 belief-observation-action 格式至关重要。

### 第二轮：决策上下文补充（仅针对含 decision 的动作）

这一轮不再是"补充遗漏"（因为 taxonomy 已经尽量覆盖了），而是专门为含决策的
动作增加**决策深度**——这直接服务于训练格式需求。

#### 产出结构

```python
class DecisionContext(BaseModel):
    """Phase 2B Round 2 产出：一个决策点的深度上下文（条件触发）。"""
    ref_seq: int = Field(ge=1, description="关联的 Action.seq")
    alternatives: list[str] = Field(
        min_length=2,
        description="未选择的备选行动，至少2个",
    )
    decision_factors: list[str] = Field(
        min_length=1,
        description=(
            "驱动实际选择的因素："
            "道德约束/性格驱动/能力限制/信息不足/情绪冲动/外部压力/过往经验"
        )
    )
    confidence: DecisionConfidence = Field(description="确信程度：坚定/犹豫/被迫/冲动")
    consequence: str = Field(description="此决定的后续影响（场景内可知）")
```

#### 决策上下文 Agent

```python
_DECISION_CONTEXT_SYSTEM_PROMPT = (
    "你是一位决策分析专家。给定一个场景和其中涉及选择/决策的动作，"
    "你为每个决策点补充备选方案、决策因素、确信程度与后续影响。"
    "你只通过 output_decision_context 工具调用输出，每个决策点单独一次调用。"
)

def extract_decision_context(
    character_profile: str,
    scene: Scene,
    decision_actions: list[Action],
    client: LLMClient,
) -> list[DecisionContext]:
    """对含决策/抑制/社会性选择的动作补充决策深度。"""
    agent = Agent(_DECISION_CONTEXT_SYSTEM_PROMPT, client=client, max_iterations=16)
    agent.add_output_tool(
        "output_decision_context",
        DecisionContext,
        "用此工具补充一个决策点的深度上下文。每个决策点单独一次调用。",
    )
    # 将动作列表序列化为可读文本
    actions_text = "\n".join(
        f"  seq={a.seq} type={a.type} description={a.description}"
        for a in decision_actions
    )
    prompt = (
        f"人物：{character_profile}\n"
        f"场景：{scene.name}\n\n"
        f"以下是此场景中涉及选择/决策的动作：\n{actions_text}\n\n"
        "对每个决策点，请补充：\n"
        "1. 备选方案：此人当时还有哪些可选行动？（至少列2个未选择的路径）\n"
        "2. 决策因素：是什么让此人选择了实际路径而非备选？\n"
        "   （道德约束/性格驱动/能力限制/信息不足/情绪冲动/外部压力/过往经验）\n"
        "3. 确信程度：此人对这个决定有多确信？（坚定/犹豫/被迫/冲动）\n"
        "4. 后续影响：这个决定导致了什么后果？（如果在当前场景内可知）"
    )
    result = agent.run(prompt, temperature=0.3)
    return result.by_tool("output_decision_context")
```

**触发条件**：只对 `type` 为 `decision`、`suppression` 或 `social` 的动作触发。
如果一个场景的动作列表中没有此类动作，跳过本轮。

#### 动作与决策上下文的缝合

```python
def enrich(
    actions: list[Action],
    decision_contexts: list[DecisionContext],
) -> list[dict]:
    """将决策上下文按 ref_seq 缝合到对应动作上。

    返回扩展后的动作列表，每个元素为 {"action": Action, "decision_context": DecisionContext | None}。
    """
    ctx_by_seq: dict[int, DecisionContext] = {
        dc.ref_seq: dc for dc in decision_contexts
    }
    return [
        {"action": a, "decision_context": ctx_by_seq.get(a.seq)}
        for a in actions
    ]
```

## 对 recurring 场景的额外处理

recurring 场景有一个独特价值：它们代表**稳态行为**。但只提取一次"典型实例"不够——
同一个反复发生的行为模式，在不同时间点可能有**微妙演变**。

#### 产出结构

```python
class SceneEvolution(BaseModel):
    """Recurring 场景额外追问产出：行为模式的演变轨迹。"""
    scene_name: str = Field(description="对应的 recurring 场景名")
    has_evolution: bool = Field(description="行为模式是否有可辨识的演变")
    trajectory: str = Field(
        default="",
        description="[如有演变] 从时期早期到晚期的变化轨迹",
    )
    exception_instance: str = Field(
        default="",
        description="[如有] 打破常规模式的特殊实例",
    )
    others_change: str = Field(
        default="",
        description="[如有] 其他在场人物反应/行为的变化",
    )
```

#### 演变追问 Agent

```python
_EVOLUTION_SYSTEM_PROMPT = (
    "你是一位行为模式分析专家。给定一个反复发生的场景及其典型动作序列，"
    "你判断该行为模式在时期进程中是否有演变，并结构化地描述演变轨迹。"
    "你只通过 output_evolution 工具调用输出结果。"
)

def extract_evolution(
    character_profile: str,
    scene: Scene,
    actions: list[Action],
    client: LLMClient,
) -> SceneEvolution:
    """对 recurring 场景追问行为演变。"""
    agent = Agent(_EVOLUTION_SYSTEM_PROMPT, client=client, max_iterations=4)
    agent.add_output_tool(
        "output_evolution",
        SceneEvolution,
        "用此工具输出 recurring 场景的行为演变分析。",
    )
    actions_text = "\n".join(
        f"  seq={a.seq} type={a.type} description={a.description}"
        for a in actions
    )
    prompt = (
        f"人物：{character_profile}\n"
        f"反复发生的场景：{scene.name}\n"
        f"典型实例的动作列表：\n{actions_text}\n\n"
        "这个场景在此时期内反复发生。请问：\n"
        "1. 从时期开始到结束，此人在这个场景中的行为模式有无演变？\n"
        "   如果有，描述从早期到晚期的变化轨迹。\n"
        "2. 有没有某一次'例外'——打破了常规模式的特殊实例？\n"
        "3. 其他在场人物的反应/行为有无随时间变化？"
    )
    result = agent.run(prompt, temperature=0.3, query_status=False)
    evolutions = result.by_tool("output_evolution")
    if evolutions:
        return evolutions[0]
    # 兜底：无明显演变
    return SceneEvolution(
        scene_name=scene.name,
        has_evolution=False,
    )
```

这一步很轻量，但产出的"行为演变弧"信息对训练 Role-Play-Agent 极有价值——
它让模型学到"角色的行为模式不是静态的，而是在 recurring 经历中逐渐位移"。

### 主循环

```python
import json
import logging
from pathlib import Path

from pydantic import ValidationError

from api import LLMClient
from character_profile import load_profile, safe_dir_name

logger = logging.getLogger(__name__)


def _load_phase1_timeline(character_dir: Path) -> Phase1Timeline:
    """读取并校验 ``phase1-timeline.json``。"""

    return Phase1Timeline.model_validate(
        json.loads((character_dir / "phase1-timeline.json").read_text(encoding="utf-8"))
    )


def _load_existing_shard(shard_path: Path) -> list["Phase2Record"] | None:
    """读取一个已存在的分片；若分片损坏则删除并返回 ``None``。"""

    try:
        return [
            Phase2Record.model_validate(item)
            for item in json.loads(shard_path.read_text(encoding="utf-8"))
        ]
    except (json.JSONDecodeError, ValidationError, KeyError, TypeError):
        logger.warning("检测到损坏分片，删除后重跑：%s", shard_path, exc_info=True)
        shard_path.unlink(missing_ok=True)
        return None


def _write_json_atomic(path: Path, records: list["Phase2Record"]) -> None:
    """先写临时文件，再原子替换目标文件，避免产生半写入分片。"""

    path.parent.mkdir(parents=True, exist_ok=True)
    tmp_path = path.with_suffix(f"{path.suffix}.tmp")
    tmp_path.write_text(
        json.dumps([record.model_dump() for record in records], ensure_ascii=False, indent=2),
        encoding="utf-8",
    )
    tmp_path.replace(path)


def _shard_path(
    character_dir: Path,
    stage_index: int,
    sub_period_index: int,
    sub_period: SubPeriodRef,
) -> Path:
    """计算子时期分片文件路径。

    双序号前缀提供稳定顺序与去冲突能力：同名子时期即便出现在不同阶段，
    文件名也不会相互覆盖。
    """

    return (
        character_dir
        / "phase2-actions"
        / f"{stage_index:02d}-{sub_period_index:02d}-{safe_dir_name(sub_period.name)}.json"
    )


def run_phase2(character_dir: Path) -> Path:
    """对 *character_dir* 中的人物执行 Phase 2 动作提取并写出结果文件。

    遵循与 :func:`extract_timeline.run` 相同的接口约定：
    读 ``gist.json`` + ``phase1-timeline.json``，写 ``phase2-actions.json``。
    """
    stored = load_profile(character_dir)
    character_context = format_character_context(stored)
    character_name = stored.profile.chinese_name

    # 从 Phase 1 JSON 反序列化为类型安全的结构
    timeline = _load_phase1_timeline(character_dir)

    all_records: list[Phase2Record] = []

    with LLMClient() as client:
        for stage_index, life_stage in enumerate(timeline.data.life_stages):
            for sub_period_index, sub_period in enumerate(life_stage.sub_periods):
                # ── 断点续跑：分片文件存在则跳过 ──
                shard_path = _shard_path(
                    character_dir,
                    stage_index,
                    sub_period_index,
                    sub_period,
                )
                if shard_path.exists():
                    existing = _load_existing_shard(shard_path)
                    if existing is not None:
                        all_records.extend(existing)
                        continue

                try:
                    # Phase 2A: 场景展开
                    if needs_scene_decomposition(sub_period, client):
                        scenes = decompose_scenes(character_context, sub_period, client)
                    else:
                        scenes = [scene_from_sub_period(sub_period, client)]

                    shard_records: list[Phase2Record] = []
                    for scene_index, scene in enumerate(scenes, start=1):
                        # Phase 2B Round 1: taxonomy 引导的全量动作提取
                        actions = extract_actions_with_taxonomy(
                            character_context, scene, sub_period, client
                        )

                        # Phase 2B Round 2: 决策上下文（条件触发）
                        decision_actions = [
                            action
                            for action in actions
                            if action.type in DECISION_RELATED_ACTION_TYPES
                        ]
                        decision_contexts: list[DecisionContext] = []
                        if decision_actions:
                            decision_contexts = extract_decision_context(
                                character_context, scene, decision_actions, client
                            )
                        ctx_by_seq = {dc.ref_seq: dc for dc in decision_contexts}

                        # Recurring 场景额外处理
                        evolution = None
                        if scene.scene_type == "recurring":
                            evolution = extract_evolution(
                                character_context, scene, actions, client
                            )

                        # ── 组装为本场景的 Phase2Record 列表 ──
                        for action in actions:
                            record = Phase2Record.from_enriched(
                                character=character_name,
                                life_stage=life_stage.name,
                                sub_period=sub_period.name,
                                scene_index_in_sub_period=scene_index,
                                scene_name=scene.name,
                                scene_type=scene.scene_type,
                                scene_time_in_period=scene.time_in_period,
                                scene_mood=scene.mood,
                                scene_sketch=scene.sketch,
                                scene_frequency=scene.frequency,
                                participants=scene.participants,
                                setting=scene.setting,
                                action=action,
                                decision_context=ctx_by_seq.get(action.seq),
                                scene_evolution=evolution,
                            )
                            shard_records.append(record)

                    # ── 子时期完成后立即写分片，实现断点续跑 ──
                    _write_json_atomic(shard_path, shard_records)
                    all_records.extend(shard_records)
                except Exception:
                    logger.warning(
                        "子时期处理失败，跳过并等待后续重跑：%s / %s",
                        life_stage.name,
                        sub_period.name,
                        exc_info=True,
                    )
                    continue

    # ── 聚合写入最终产出 ──
    output_path = character_dir / "phase2-actions.json"
    _write_json_atomic(output_path, all_records)
    return output_path
```

### 产出文件格式

Phase 2 产出两种文件，均位于人物目录下：

## 调用量估算（简·爱为例）

以下按 24 个子时期、~170 个场景、~30 个 recurring 场景估算。
`query_status` 列标注该 Agent 是否启用默认的状态查询追加轮（`temperature=0.0`、
单次工具调用，开销极轻量）。

```
Phase 2A 判断 (needs_scene_decomposition, query_status=False):
  24个子时期 × 1次调用 = 24次

Phase 2A 场景展开 (decompose_scenes):
  ~15个需要展开的子时期 × 1次调用 = 15次
  + 15次状态查询 (query_status=True, 默认)

Phase 2A 单场景转换 (scene_from_sub_period, query_status=False):
  ~9个单场景子时期 × 1次调用 = 9次

Phase 2B Round 1: 动作提取 (extract_actions_with_taxonomy):
  ~170个场景 × 1次调用 = 170次
  + 170次状态查询 (query_status=True, 默认)

Phase 2B Round 2: 决策上下文 (extract_decision_context):
  预计60%的场景有决策动作 → ~100次调用
  + 100次状态查询 (query_status=True, 默认)

Recurring 演变追问 (extract_evolution, query_status=False):
  预计~30个recurring场景 × 1次调用 = 30次

────────────────────────────────────────
有效分析调用: 24+15+9+170+100+30 = 348次
状态查询追加: 15+170+100 = 285次 (极轻量)
单人物总计: ~633次调用
5000人物总计: ~3,165,000次调用
```

> **优化建议**：若需控制预算，可将 `decompose_scenes`、`extract_actions_with_taxonomy`、
> `extract_decision_context` 的 `query_status` 关闭（传 `query_status=False`），
> 但会丢失结构化的任务成败信号——建议至少在试点阶段保留，以便监控各 Agent 的健康度。
> 关闭后可节省约 285 次/人物（45% 开销），总调用降至 ~348 次/人物、~1,740K/5000 人物。

相比之前两个方案：
| 方案 | 单人物有效调用 | 单人物含状态查询 | 总调用(5000人,含状态查询) |
|------|--------------|-----------------|-------------------------|
| 多轴交叉 | ~100 | ~100 | ~500K |
| 我之前的三轮方案 | ~180 | ~180 | ~900K |
| 思路二（场景+taxonomy） | ~200（估） | ~200（估） | ~1000K |
| **综合方案** | **~348** | **~633** | **~3,165K** |

调用量最高，但每次调用的产出质量和可用性也最高——因为：
1. 场景层确保了不跳过任何时间段
2. Taxonomy 确保了不遗漏任何动作维度
3. 决策上下文直接可用于 belief-observation-action 格式转换
4. Recurring 演变数据提供了行为弧的训练信号

如果需要控制预算，**最该砍的是 Round 2 的触发比例**——可以从"60%场景"降到"只对明确有重大决策的场景触发"，能砍掉约30%调用。
其次可关闭 `query_status`（见上文优化建议），再砍约 45%。

## 去重策略

> **归属说明**：去重策略在此描述以保持设计完整性，但具体实现（embedding 模型选型、
> 阈值调参、"关联动作"标记的存储格式）属于 **Phase 5 预处理步骤**，不在 Phase 2 范围内。
> Phase 2 的职责是尽可能完整地产出动作序列；Phase 5 负责清洗和去重。

这个方案下去重更简单：

**结构性去重（规则，Phase 2 prompt 层面处理）：**
- 相邻子时期的 closing/opening 重叠：允许偶发重叠，优先保证关键转折动作不丢失。
  在 2A prompt 中指示 LLM 将 opening_event 作为本时期第一个场景的核心内容自然展开；
  若同一事件在相邻子时期边界处被两次覆盖（从不同视角或粒度），Phase 5 的语义去重会处理。
- 场景展开时与 opening/closing event 的关系：opening_event 和 closing_event 是必须覆盖的
  转折锚点——宁可边界处偶有重叠，也不能因回避重复而遗漏关键转折动作。

**语义去重（后处理，Phase 5 实现）：**
- 对全量动作做 embedding
- 同一子时期内 cosine similarity > 0.92 的动作对，取描述更具体的那个
- 跨子时期的高相似动作，保留两个但标记为"关联动作"（可能是同一行为模式在不同时期的体现，不应该删除）

### Phase 2 最终产出的 Pydantic 模型

上述 JSON 预览对应的正式模型定义如下。该模型是 Phase 2 的**可交付物**——
每条记录自包含所有上下文字段，不依赖外部 join：

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional


class Phase2Record(BaseModel):
    """Phase 2 最终产出：一条附着完整上下文的动作记录。

    每条记录对应一个场景内的一个动作单元，携带其所属的 life_stage、
    sub_period、scene 的全部上下文，以及可选的决策深度和场景演变信息。
    """

    # ── 人物标识 ──
    character: str = Field(description="人物中文名")

    # ── 时间轴上下文（来自 Phase 1） ──
    life_stage: str = Field(description="所属主要人生阶段名")
    sub_period: str = Field(description="所属子时期名")

    # ── 场景上下文（来自 Phase 2A） ──
    scene_index_in_sub_period: int = Field(
        ge=1,
        description="该场景在所属 sub_period 内的顺序号，从 1 开始",
    )
    scene_name: str = Field(description="所属场景名")
    scene_type: SceneType = Field(
        description="场景类型：singular=一次性事件，recurring=反复发生的行为模式"
    )
    scene_time_in_period: str = Field(default="", description="场景在子时期中的相对时间位置")
    scene_mood: str = Field(default="", description="场景主基调")
    scene_sketch: str = Field(description="场景概述，保留 Phase 2A 的原始摘要")
    scene_frequency: str = Field(
        default="",
        description="[仅 recurring] 大约发生的频率和持续时间跨度；singular 场景留空",
    )
    participants: list[str] = Field(default_factory=list, description="场景在场人物")
    setting: str = Field(default="", description="场景地点/环境")

    # ── 动作本体（来自 Phase 2B Round 1） ──
    seq_in_scene: int = Field(ge=1, description="在场景内的顺序号，从 1 开始")
    action_type: ActionType = Field(
        description=(
            "动作类型，14 类 taxonomy 之一："
            "verbal / physical / social / instrumental / expressive / "
            "perception / interpretation / emotion / recall / judgment / "
            "decision / desire / suppression / belief_update"
        )
    )
    action_description: str = Field(description="动作的具体描述，一句话")
    action_detail: str = Field(default="", description="可选的补充细节或上下文")

    # ── 决策上下文（来自 Phase 2B Round 2，条件存在） ──
    decision_alternatives: list[str] = Field(
        default_factory=list,
        description="[如有] 未选择的备选行动",
    )
    decision_factors: list[str] = Field(
        default_factory=list,
        description="[如有] 驱动实际选择的因素",
    )
    decision_confidence: DecisionConfidence | None = Field(
        default=None,
        description="[如有] 确信程度：坚定/犹豫/被迫/冲动",
    )
    decision_consequence: str = Field(
        default="",
        description="[如有] 此决定的后续影响（场景内可知）",
    )

    # ── 场景演变（来自 recurring 追问，条件存在） ──
    scene_has_evolution: bool = Field(
        default=False,
        description="[仅 recurring] 行为模式是否有可辨识的演变",
    )
    scene_evolution_trajectory: str = Field(
        default="",
        description="[如有演变] 从时期早期到晚期的变化轨迹",
    )
    scene_evolution_exception: str = Field(
        default="",
        description="[如有] 打破常规模式的特殊实例",
    )
    scene_evolution_others_change: str = Field(
        default="",
        description="[如有] 其他在场人物反应/行为的变化",
    )


    @classmethod
    def from_enriched(
        cls,
        *,
        character: str,
        life_stage: str,
        sub_period: str,
        scene_index_in_sub_period: int,
        scene_name: str,
        scene_type: SceneType,
        scene_time_in_period: str,
        scene_mood: str,
        scene_sketch: str,
        scene_frequency: str,
        participants: list[str],
        setting: str,
        action: "Action",
        decision_context: Optional["DecisionContext"] = None,
        scene_evolution: Optional["SceneEvolution"] = None,
    ) -> "Phase2Record":
        """从 Phase 2 各子阶段产出的分散对象组装为一条完整记录。"""
        return cls(
            character=character,
            life_stage=life_stage,
            sub_period=sub_period,
            scene_index_in_sub_period=scene_index_in_sub_period,
            scene_name=scene_name,
            scene_type=scene_type,
            scene_time_in_period=scene_time_in_period,
            scene_mood=scene_mood,
            scene_sketch=scene_sketch,
            scene_frequency=scene_frequency,
            participants=list(participants),
            setting=setting,
            seq_in_scene=action.seq,
            action_type=action.type,
            action_description=action.description,
            action_detail=action.detail,
            decision_alternatives=decision_context.alternatives if decision_context else [],
            decision_factors=decision_context.decision_factors if decision_context else [],
            decision_confidence=decision_context.confidence if decision_context else None,
            decision_consequence=decision_context.consequence if decision_context else "",
            scene_has_evolution=scene_evolution.has_evolution if scene_evolution else False,
            scene_evolution_trajectory=scene_evolution.trajectory if scene_evolution else "",
            scene_evolution_exception=scene_evolution.exception_instance if scene_evolution else "",
            scene_evolution_others_change=scene_evolution.others_change if scene_evolution else "",
        )
```

> **关于 `action.subtype` 和 `emotional_state`**：这两个字段不在 Phase 2 产出中。
> `subtype`（如 `type=social` → `subtype=反抗`）和 `emotional_state`（从场景中
> 所有 `type=emotion` 的动作合成一条概括性情绪弧线）属于 **Phase 5** 的职责——
> Phase 5 可用一次轻量 LLM 调用或规则引擎从 Phase 2 产出的动作序列中推导。

### Phase 2 与 Phase 5 的边界

**Phase 2 的范围（本文档所覆盖）**：
- 场景展开（2A）→ 动作提取（2B R1）→ 决策上下文补充（2B R2）→ recurring 演变追问
- 产出：`Phase2Record` 列表，每条记录是附着完整上下文的单个动作单元；保留 scene 顺序、time_in_period、frequency 与 recurring 演变信息，避免 Phase 2A 信息在扁平化时丢失
- **去重**：本文档仅描述去重策略的思路（结构性去重 + 语义去重），具体实现
  （embedding 模型选型、阈值调参、"关联动作"标记机制）属于 Phase 5 预处理步骤，
  不在 Phase 2 范围内。

**Phase 5 的范围（后续设计，不在本文档）**：
- 语义去重的具体实现
- `action.subtype` 推导
- `emotional_state` 合成
- `Phase2Record` → belief-observation-action 训练格式的完整转换
- 训练/验证集划分

这个结构到 Phase 5 时，几乎是直接映射的——
scene 上下文 → belief，前序动作链 → observation 的一部分，
action + decision_context → 完整的 action 输出（含推理过程）。

## 断点续跑与错误恢复

对于 5000 人物的规模，管线必然会中途失败（API 限流、网络中断、单次 Agent
超时、单人物 token 预算耗尽等）。以下方案在实现复杂度与可靠性之间取平衡。

### 核心机制：分片文件即进度标记（checkpoint-by-product）

**原则**：每个子时期处理完毕后立即将其 ``Phase2Record`` 列表写为独立分片文件；
重跑时扫描已存在的分片文件并跳过对应子时期。不引入额外的进度文件——分片文件
的存在性本身就是进度状态。

**分片粒度**：子时期级。场景级太重（分片过多、IO 开销大），人物级太粗
（一个人物中途失败则整人物重来）。子时期级在两者之间取得平衡。

**文件路径**：`{character_dir}/phase2-actions/{stage:02d}-{sub:02d}-{safe_sub_period_name}.json`

### 失败处理策略

**子时期级脏状态**：
- 若子时期处理中途失败（如场景已展开但动作提取时 API 超时），分片文件尚未写出，
  重跑时该子时期不存在分片 → 自动从头重来。
- 若分片文件已写出但内容不完整（写盘时进程崩溃），文件存在但 JSON 解析失败 →
  视为脏数据，删除分片文件后重来。实现时应在 ``shard_path.exists()`` 分支中包裹
    ``try/except (json.JSONDecodeError, ValidationError, KeyError, TypeError)``，
    解析或模型校验失败则 ``shard_path.unlink(missing_ok=True)`` 后继续正常流程。

**Agent.run 失败后的重试**：
- 每个 Agent.run 由 :class:`agent.Agent` 内部的重试机制覆盖（模型返回错误时通过
  tool result 反馈自愈）；若整个 ``run()`` 抛异常（如网络中断），在子时期外层
  包裹 ``try/except``，失败则记录告警并跳过该子时期（不写分片），由后续重跑覆盖。
- 重试次数与退避：单次 Agent.run 内由 ``LLMClient`` 的 tenacity 装饰器处理
    （已在 :mod:`api` 中配置：指数退避、最大 5 次重试、仅对可重试状态码）。
  不额外引入 Agent 级重试循环——保持简单。

### 并行粒度

**推荐**：按人物并行（人物间无依赖），人物内部子时期间严格串行。

- 人物间并行可直接用 ``concurrent.futures.ThreadPoolExecutor``（与 ``make_dir.py``
  相同的模式），每个 worker 独占一个 ``LLMClient``。
- 人物内部串行的原因：LLM API 的 rate limit 是主要瓶颈，子时期间并行会导致
  同一人物的 N 个请求同时涌入，增加 429 概率而非提高吞吐。
- 若后续观察到 rate limit 余量充足，可将子时期间也并行（子时期间无数据依赖），
  但需额外处理分片文件的并发写入安全（加锁或使用临时文件 + 原子 rename）。

### 聚合与收尾

全部子时期分片写完后，按 life_stage → sub_period 的顺序读取所有分片并拼合为
``phase2-actions.json``（人物级聚合文件，供 Phase 5 消费）。分片文件保留不删，
便于增量重跑时跳过已完成的子时期。

### 逐子时期执行摘要

```
for each sub_period:
    1. 计算分片路径 shard_path
    2. if shard_path 存在且 JSON 合法 → 加载已有记录，continue
    3. if shard_path 存在但 JSON 非法 → 删除 shard_path（脏数据清理）
    4. 执行 Phase 2A → 2B R1 → 2B R2 → recurring 演变
    5. 组装 Phase2Record 列表 → 写入 shard_path（原子性：先写 .tmp 再 rename）
    6. 将本子时期记录追加到内存中的 all_records
```

> **为什么不用进度文件**：分片文件同时承载数据与进度标记，避免进度文件与分片文件
> 不一致的经典问题（进度文件标记 done 但分片文件写入失败/不完整）。单一事实来源
> （分片文件）更简单可靠。
