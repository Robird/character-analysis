# 综合改进方案：场景展开 + 三轮递进提取

两个思路的优势互补很清晰：

- **思路二的优势**：场景中间层的设计（特别是 recurring/singular 的区分）、动作类型分类框架（action_taxonomy）作为结构化引导
- **我之前思路的优势**：三轮递进提取（叙事→维度补充→未选择路径）、对长周期子时期的处理、第三轮的"决策上下文"对训练数据格式的直接贡献

合并后的核心架构：

```
sub_period
  └─ Phase 2A: 场景展开（含 recurring/singular 标注）
       └─ Phase 2B: 动作提取（三轮递进，以 taxonomy 为引导框架）
            └─ Phase 2C: 决策上下文补充（未选择路径，仅对决策类动作）
```

## Phase 2A：场景展开

基本沿用思路二的设计，做几个改进：

```yaml
prompt: |
  人物：{character}
  时期：{sub_period.name}
  时间范围：{sub_period.time_range}
  处境：{sub_period.core_situation}
  起始事件：{sub_period.opening_event}
  结束事件：{sub_period.closing_event}

  请将此时期展开为一个有序的场景序列。
  每个场景是一个时空连续的、可"拍成一个镜头"的具体事件或情境。

  要求：
  1. 覆盖此时期的完整时间线，不跳过"平淡"的部分
  2. 标志性事件、日常典型情境、过渡场景都要包括
  3. 对长时间跨度中反复发生的行为模式，用"典型场景"来代表
  4. 场景之间保持时间/因果顺序
  5. 每个场景包含以下字段：

  输出格式（JSON数组）：
  [
    {
      "name": "场景名",
      "scene_type": "singular | recurring",
      "time_in_period": "此场景在子时期中的相对时间位置",
      "participants": ["在场人物"],
      "setting": "地点/环境",
      "mood": "主基调",
      "sketch": "50-80字的场景概述，描述发生了什么"
    }
  ]

  对于 scene_type 为 recurring 的场景：
  - 说明大约发生的频率和持续时间跨度
  - sketch 描述一次"典型实例"的情形

  目标数量：根据时期跨度自适应
  - 单日/单场景的子时期：不需要展开，输出 null
  - 数周跨度：5-8个场景
  - 数月跨度：8-12个场景
  - 数年跨度：12-18个场景
```

**改进点**：加了 `time_in_period` 字段（方便后续动作排序）、用 LLM Agent 做单场景判定替代硬编码关键词匹配（见下方「跳过逻辑」）、输出格式指定为 JSON 方便管线解析。

### 跳过逻辑

不依赖硬编码关键词，改用 LLM Agent 做结构化判断——与 Phase 0 的
`extract_meta`、Phase 1 的时间线划分保持一致的 Agent 调用范式。

先定义产出结构：

```python
from pydantic import BaseModel, Field

class SceneDecompositionVerdict(BaseModel):
    """对单个子时期是否需要场景展开的结构化判断。"""
    needs_decomposition: bool = Field(description="是否需要场景展开")
    reason: str = Field(description="判断依据，如'单日内的单一事件'或'跨度数年的漫长时期'")
```

Agent 构造与判断函数：

```python
from agent import Agent

_SCENE_DECOMP_SYSTEM_PROMPT = (
    "你是一个文本分析辅助程序。你的任务是根据子时期的时间范围描述，"
    "判断该子时期是否需要进行场景展开（decomposition）。"
    "规则：如果时间范围描述表明这是一个单日/单场景的短事件"
    "（如'一个傍晚''当天下午''那个凌晨''某次交谈'），则不需要展开；"
    "如果时间跨度达到数周或更长，则需要展开。"
    "你只通过工具调用输出判断结果，不输出其他内容。"
)

def needs_scene_decomposition(sub_period, client: LLMClient) -> bool:
    """用 LLM Agent 判断子时期是否需要场景展开。"""
    agent = Agent(_SCENE_DECOMP_SYSTEM_PROMPT, client=client, max_iterations=4)
    agent.add_output_tool(
        "output_verdict",
        SceneDecompositionVerdict,
        "用此工具输出对当前子时期是否需要场景展开的判断。",
    )
    prompt = (
        f"子时期名称：{sub_period.name}\n"
        f"时间范围描述：{sub_period.time_range}\n"
        f"核心处境：{sub_period.core_situation}\n\n"
        "请判断此子时期是否需要场景展开。"
    )
    result = agent.run(prompt, temperature=0.0, query_status=False)
    verdicts = result.by_tool("output_verdict")
    if not verdicts:
        # 兜底：未能取得结构化判断时，保守地展开
        return True
    return verdicts[-1].needs_decomposition
```

为什么改用 LLM Agent：

- 关键词匹配无法可靠地区分「三年流浪」「数月漂泊」（需要展开）与「某个秋日午后」
  （不需要展开）——两者的自然语言时间粒度差异只能由语义理解捕获。
- 产出带有 `reason` 字段，方便审计与调试——知道 LLM *为什么* 做了某个判断。
- 与管线其他 Agent 调用（Phase 0 的元信息提取、Phase 2A/2B/2C 的主体分析）
  共用同一 `LLMClient`，不引入新依赖。
- 此判断任务极轻量（单次调用、`temperature=0.0`、`max_iterations=4`），
  对于 5000 人物 × 平均 8 个子时期 = ~40K 次额外调用，在总体预算中占比微小。

对于简·爱的24个子时期，大约：
- 8-10个是单场景（红房子事件、果园求婚、婚礼中断、重逢等）→ 跳过，直接进 2B
- 14-16个需要展开 → 每个产出 5-18 个场景

预计总场景数：~8 个直通 + ~160 个展开 = **约 170 个场景单元**

## Phase 2B：动作提取（核心改进——融合两种思路）

这里是最关键的融合。思路二的 action_taxonomy 作为**引导框架**，我之前的三轮递进改造为**两轮**（因为 taxonomy 本身已经覆盖了"维度补充"的大部分功能，不需要独立的第二轮了）。

### 第一轮：以 taxonomy 引导的全量提取

```yaml
prompt: |
  人物：{character}
  场景：{scene.name}
  场景类型：{scene.scene_type}
  在场人物：{scene.participants}
  环境：{scene.setting}
  基调：{scene.mood}
  概述：{scene.sketch}

  所属子时期背景：{sub_period.core_situation}

  请列举 {character} 在此场景中的全部动作，包括外部动作和内部动作。
  按时间/因果顺序排列，每个动作标注类型。

  动作类型参考（每种类型都考虑是否存在，但不强求每种都有）：

  外部动作：
  - verbal: 说了什么（对谁、什么语气、什么意图）
  - physical: 身体动作、位移、姿态
  - social: 人际交互行为（服从/反抗/讨好/回避/合作/对抗）
  - instrumental: 使用物品、读写、劳作
  - expressive: 非言语情绪表达（哭、笑、沉默、颤抖、叹息）

  内部动作：
  - perception: 注意到/观察到了什么
  - interpretation: 如何理解当前情境
  - emotion: 产生什么情绪、情绪如何变化
  - recall: 想起了什么
  - judgment: 对人或事做出什么评价
  - decision: 做了什么决定（包括"决定忍耐""决定不说"）
  - desire: 想要什么、渴望什么
  - suppression: 压抑了什么冲动
  - belief_update: 信念/认知是否发生变化

  输出格式：
  [
    {
      "seq": 1,
      "type": "physical",
      "description": "简缩在窗帘后面，将双腿蜷起贴在胸前",
      "detail": "可选的补充细节或上下文"
    },
    ...
  ]

  注意：
  - 如果场景类型是 recurring，描述的是一次典型实例中的动作序列
  - 粒度要求：一个动作 ≈ 一个可观察的行为单元或一次内心转变
  - 不要合并多个动作为一条笼统描述
  - 预期产出 15-30 个动作
```

**相比纯三轮方案的改进**：taxonomy 把"第二轮维度补充"直接前置为引导框架，减少了一轮调用。LLM 在第一轮就被迫覆盖各个维度，而不是先产出显著动作再补充。

**相比纯 taxonomy 方案的改进**：保留了叙事顺序（"按时间/因果顺序排列"），使产出天然具有序列结构，而不是按类型分桶堆砌——这对后续转换为 belief-observation-action 格式至关重要。

### 第二轮：决策上下文补充（仅针对含 decision 的动作）

这一轮不再是"补充遗漏"（因为 taxonomy 已经尽量覆盖了），而是专门为含决策的动作增加**决策深度**——这直接服务于你的训练格式需求：

```yaml
prompt: |
  人物：{character}
  场景：{scene.name}

  以下是此场景中提取到的涉及选择/决策的动作：
  {filtered_actions_with_decision_or_suppression}

  对每个决策点，请补充：

  1. 备选方案：此人当时还有哪些可选行动？（至少列2个未选择的路径）
  2. 决策因素：是什么让此人选择了实际路径而非备选？
     （道德约束 / 性格驱动 / 能力限制 / 信息不足 / 情绪冲动 / 外部压力 / 过往经验）
  3. 确信程度：此人对这个决定有多确信？（坚定 / 犹豫 / 被迫 / 冲动）
  4. 后续影响：这个决定导致了什么后果？（如果在当前场景内可知）

  输出格式：
  [
    {
      "ref_seq": 12,
      "alternatives": ["默默忍受不反抗", "向旁边的仆人求助"],
      "decision_factors": ["痛苦累积超过阈值", "对不公正的本能愤怒"],
      "confidence": "冲动——事后可能感到惊讶于自己的反应",
      "consequence": "被里德太太惩罚关入红房子"
    },
    ...
  ]
```

**这一轮是有选择性的**——只对含 `decision`、`suppression` 或 `social`（含选择性）的动作触发。如果一个场景的动作列表中没有决策类动作（比如纯被动经历的场景），则跳过这轮。

## 对 recurring 场景的额外处理

recurring 场景有一个独特价值：它们代表**稳态行为**。但只提取一次"典型实例"不够——同一个反复发生的行为模式，在不同时间点可能有**微妙演变**。

对每个 recurring 场景，追加一个轻量prompt：

```yaml
prompt: |
  人物：{character}
  反复发生的场景：{scene.name}
  典型实例的动作列表：{round_1_actions}

  这个场景在此时期内反复发生。请问：

  1. 从时期开始到结束，此人在这个场景中的行为模式有无演变？
     如果有，描述从早期到晚期的变化轨迹。
  2. 有没有某一次"例外"——打破了常规模式的特殊实例？
  3. 其他在场人物的反应/行为有无随时间变化？

  如果无明显变化，回答"无显著演变"即可。
```

这一步很轻量，但产出的"行为演变弧"信息对训练 Role-Play-Agent 极有价值——它让模型学到"角色的行为模式不是静态的，而是在 recurring 经历中逐渐位移"。

## 整合后的管线流程

```python
client = LLMClient()

for character in characters:
    timeline = load_phase1(character)
    all_actions = []
  
    for sub_period in timeline.sub_periods:
        # Phase 2A: 场景展开（LLM Agent 判断，替代关键词匹配）
        if needs_scene_decomposition(sub_period, client):
            scenes = decompose_scenes(character, sub_period)
        else:
            # 单场景子时期，直接用 sub_period 自身信息构造一个 scene
            scenes = [scene_from_sub_period(sub_period)]
      
        for scene in scenes:
            # Phase 2B Round 1: taxonomy引导的全量提取
            actions = extract_actions_with_taxonomy(character, scene, sub_period)
          
            # Phase 2B Round 2: 决策上下文（条件触发）
            decision_actions = [a for a in actions if a.type in ('decision', 'suppression', 'social')]
            if decision_actions:
                decision_context = extract_decision_context(character, scene, decision_actions)
                enrich(actions, decision_context)
          
            # Recurring 场景额外处理
            if scene.scene_type == "recurring":
                evolution = extract_evolution(character, scene, actions)
                actions.append_metadata(evolution)
          
            all_actions.extend(actions)
  
    # 后处理
    deduplicated = semantic_dedup(all_actions)
    training_samples = convert_to_belief_observation_action(deduplicated, timeline)
```

## 调用量估算（简·爱为例）

```
Phase 2A: 场景展开
  ~15个需要展开的子时期 × 1次调用 = 15次

Phase 2B Round 1: 动作提取
  ~170个场景 × 1次调用 = 170次

Phase 2B Round 2: 决策上下文
  预计60%的场景有决策动作 → ~100次调用

Recurring 演变追问:
  预计~30个recurring场景 × 1次调用 = 30次

单人物总计: ~315次调用
5000人物: ~1,575,000次调用
```

相比之前两个方案：
| 方案 | 单人物调用 | 总调用(5000人) |
|------|-----------|---------------|
| 多轴交叉 | ~100 | ~500K |
| 我之前的三轮方案 | ~180 | ~900K |
| 思路二（场景+taxonomy） | ~200（估） | ~1000K |
| **综合方案** | **~315** | **~1,575K** |

调用量最高，但每次调用的产出质量和可用性也最高——因为：
1. 场景层确保了不跳过任何时间段
2. Taxonomy 确保了不遗漏任何动作维度
3. 决策上下文直接可用于 belief-observation-action 格式转换
4. Recurring 演变数据提供了行为弧的训练信号

如果需要控制预算，**最该砍的是 Round 2 的触发比例**——可以从"60%场景"降到"只对明确有重大决策的场景触发"，能砍掉约30%调用。

## 去重策略

这个方案下去重更简单：

**结构性去重（规则）：**
- 相邻子时期的 closing/opening 重叠：在 2A prompt 中明确指示"本时期从 opening_event 之后开始，opening_event 本身已被上一时期覆盖"
- 场景展开时与 opening/closing event 的重叠：同上，在 prompt 中排除

**语义去重（后处理）：**
- 对全量动作做 embedding
- 同一子时期内 cosine similarity > 0.92 的动作对，取描述更具体的那个
- 跨子时期的高相似动作，保留两个但标记为"关联动作"（可能是同一行为模式在不同时期的体现，不应该删除）

## 最终产出格式预览

单个动作的完整数据结构（Phase 2 产出，供 Phase 5 转换用）：

```json
{
  "character": "简·爱",
  "life_stage": "盖茨黑德时期",
  "sub_period": "红房子事件与觉醒反抗",
  "scene": "约翰殴打与简的反击",
  "scene_type": "singular",
  "seq_in_scene": 7,
  "action": {
    "type": "social",
    "subtype": "反抗",
    "description": "简猛扑向约翰·里德，用拳头击打他，嘴里喊着'你是恶毒的残忍的孩子'",
    "detail": "这是简第一次对约翰的暴力进行肉体反击，而非像以往那样默默忍受"
  },
  "decision_context": {
    "alternatives": ["像往常一样默默忍受", "哭泣求饶", "向仆人求助"],
    "decision_factors": ["痛苦累积超过阈值——被书砸中太阳穴出血", "长期不公正的愤怒总爆发"],
    "confidence": "冲动——非理性的爆发，事后自己也震惊",
    "consequence": "被仆人制服，被里德太太下令关入红房子"
  },
  "participants": ["约翰·里德", "贝茜", "阿伯特小姐"],
  "setting": "盖茨黑德早餐室",
  "emotional_state": "从恐惧瞬间转为暴怒"
}
```

这个结构到 Phase 5（转换为 belief-observation-action）时，几乎是直接映射的——scene 上下文 → belief，前序动作链 → observation 的一部分，action + decision_context → 完整的 action 输出（含推理过程）。
